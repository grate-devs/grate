# WinGet identity migration preparation (#800)

Status: preparation only. `erikbra.grate` remains the release identity.
`grate-devs.grate` is a proposed new package, not an alias or an in-place rename.
Do not advertise or submit it until Windows migration tests and upstream review
have resolved the correlation contract below. Keep the old listing during the
transition; removal is a separate decision with WinGet maintainers.

Checked on 2026-11-01:

  rejects releases without the current five-asset inventory.

## Compatibility contract

### Portable ZIPs

The client derives portable registration identity from package ID **and source**,
and checks both against existing registration. See
[PortableFlow.cpp](https://github.com/microsoft/winget-cli/blob/master/src/AppInstallerCLICore/Workflows/PortableFlow.cpp).
Consequently an upgrade of `erikbra.grate` cannot be assumed to discover or
transfer to `grate-devs.grate`. A local `winget install --manifest` uses a
different source identity from the community repository, so it is only rehearsal
evidence, not proof of a community-source transition.

Proposed supported transition: explicit uninstall of the old portable package,
then install of the accepted new ID. Keep the `grate` command name. Do not use
`--force` to overwrite registration or allow competing command links. Existing
exports/imports retain the old ID while the old listing remains available.

### MSI

The WinGet ID does not change Windows Installer identity. Preserve these values:

| Field | Existing authoring contract |
| --- | --- |
| ProductCode | `{E281998A-D8A2-4926-AAA3-066EFA4B2E74}` for both architectures |
| ProductName / Manufacturer | `grate` / `erikbra` |
| Scope / privileges | per-user / limited |
| Install directory | `%LOCALAPPDATA%\erikbra\grate` |
| Marker | `HKCU\Software\Microsoft\erikbra\grate` |
| UpgradeCode | A fresh GUID by default on every build; inspect each actual MSI |
| PackageCode | Generated by WiX; inspect each actual MSI |

The fixed ProductCode, changing UpgradeCodes, and absence of an Upgrade table
mean that simply adding `MajorUpgrade`, changing Manufacturer, or allocating a
new ProductCode is not a compatibility fix. This change preserves the installer
and adds read-only inspection plus guards against accidental identity edits.
It does not establish a working WinGet MSI upgrade.

The [WinGet publisher-transition FAQ](https://github.com/microsoft/winget-pkgs/blob/master/doc/FAQ.md#what-should-i-do-if-a-package-is-being-published-by-a-new-publisher)
describes an ARP-driven transition using both IDs and different metadata in the
old and new listings. That recipe assumes an actual ARP publisher transition.
Our MSI still reports `erikbra`; changing only the locale Publisher field does
not change it. The candidate deliberately retains real MSI correlation metadata.

Identical ProductCode/UpgradeCode matches under two IDs can also make correlation
ambiguous; see [CompositeSource.cpp](https://github.com/microsoft/winget-cli/blob/master/src/AppInstallerRepositoryCore/CompositeSource.cpp).
**Do not submit the generated five-installer candidate unchanged as proof of a
working dual-listing transition.** Agree the old/new MSI matching strategy with
maintainers and verify both listings together before submission. Until then,
uninstall/reinstall is the conservative proposed fallback for MSI as well.
Normal same-ID MSI updates also need testing: explicit minor-update switches
(`REINSTALL=ALL REINSTALLMODE=vomus`) or `UpgradeBehavior: uninstallPrevious`
are possibilities, not enabled or verified by this preparation.

## Generate a local proposal

On Windows with wingetcreate available:

```powershell
# Update the accepted ID locally. Does not submit.
./installers/winget/Create-Installer.ps1 -version 2.1.6

# Separate new-package candidate. Does not submit or touch historical manifests.
./installers/winget/Create-Installer.ps1 -version 2.1.6 -PrepareMigration -outputDirectory ./candidate
```

Both commands fetch the actual published GitHub release inventory, reject drafts
and prereleases, and require all five uploaded assets. wingetcreate downloads
the assets, calculates hashes and reads installer metadata. The new-package mode
uses `update erikbra.grate` as an upstream template, then changes only the package
ID, filenames, partition and locale Publisher. It never calls
`update grate-devs.grate` before that ID exists. Existing output is not overwritten.
See [wingetcreate update](https://github.com/microsoft/winget-create/blob/main/doc/update.md).

The dedicated `WinGet manifest preparation` workflow uses pinned wingetcreate
1.12.13.0 and release 2.1.6. It retains both manifest sets, logs and read-only
Windows MSI metadata as a `winget-preparation` artifact. This job has read-only
repository permissions and no submission, installer execution or release steps.

Local contract checks:

```powershell
./installers/winget/Test-CreateInstaller.Tests.ps1
./installers/msi/Test-InstallerAuthoring.Tests.ps1
```

## Required Windows evidence before activation

Use disposable Windows systems. Record OS/architecture, WinGet version and source
ID, old/new release versions, both manifest revisions, installer hashes, exit
codes, verbose installer logs, ARP entries, `winget list`, `winget upgrade`,
`winget export`, `Get-Command grate -All`, `where.exe grate` and `grate --version`.

| Boundary | Cases and assertions still required |
| --- | --- |
| Portable same-ID upgrade | x86/x64 on Windows x64, arm64 on native Windows arm64; installed old community package upgrades without switching installer type, losing registration or creating duplicate command links |
| Portable identity transition | Both IDs visible in the same source; observe attempted new-ID upgrade, then test explicit old-ID uninstall/new-ID install and final cleanup; repeat against the community source after acceptance |
| MSI same-ID upgrade | Historical 1.2.0 x64, 2.0.0 and 2.1.6 x64/arm64 to the candidate built from current main; inspect each actual ProductCode/UpgradeCode/PackageCode and validate actual binary replacement and ARP version |
| MSI identity transition | Both IDs visible simultaneously; test detection before/after new-ID install and upgrade; require unambiguous correlation, one installation/ARP product and correct payload; verify uninstall/reinstall fallback |
| Installed behavior and data | Run SQLite migration and rerun using installed grate, preserve DB/scripts outside the installation directory, verify PATH resolution and uninstall removes the intended payload/registration |
| New source listing | After upstream acceptance, `winget show --exact --id grate-devs.grate --source winget` and repeat source-dependent migration checks |

Example fallback commands **for testing after the new ID is available**, selecting
the same architecture and installer type as the old installation:

```powershell
winget uninstall --exact --id erikbra.grate --source winget
winget install --exact --id grate-devs.grate --source winget --architecture x64 --installer-type zip --scope user
# For an MSI installation, select --installer-type wix instead of zip.
```

Confirm the old installation and command link were removed before the install.
MSI authoring currently makes its user PATH entry permanent; uninstall/reinstall
testing must check for stale entries explicitly. Do not delete migration data.

## Handoff to the shared release/documentation track

Do not copy the old draft #804 pipeline wholesale. Preserve main's .NET 11 RC3,
servicing, package and installer work. No `build.yml`, README or general release
documentation has been changed by this branch.

For a preparation job in the shared release workflow:

1. Depend on version calculation, Windows standalone ZIP publication and both
   MSI uploads. The helper needs public assets, not just Actions artifacts.
2. Require `is-release == 'true'` **and** a stable full version: for current
   GitVersion outputs, `semVer == nuGetVersion`. The helper independently checks
   version/tag syntax and GitHub's draft/prerelease flags. Pass the actual release
   tag separately if it has a `v` prefix.
3. Call `Create-Installer.ps1 -version <nuGetVersion> -releaseTag <semVer>` and
   upload the generated artifact. This continues preparing `erikbra.grate`.
4. Keep submission separate. This branch adds no publishing credentials, token
   arguments or auto-submission. Existing authorized publication of the legacy
   identity need not be switched merely to merge preparation tooling.
5. Activate the new ID only in a later reviewed change after Windows evidence,
   upstream acceptance and community-source visibility. Retain an explicit old-ID
   compatibility plan during the overlap; no automatic retirement or manifest
   deletion. Then update the helper's normal update target and the release job
   together, and change user-facing docs in the shared track.

Issue #800 remains open until its Windows, upstream acceptance, publishing and
documentation acceptance criteria are met.
