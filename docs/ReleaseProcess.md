# Release process

This document describes the release process introduced for
[issue #796](https://github.com/grate-devs/grate/issues/796).

## Goals

- Use a published GitHub release and its tag as the source of truth for the version.
- Build the same packages and platform artifacts in pull requests and releases.
- Publish all supported distribution formats from one release workflow.
- Support SemVer prereleases, including NuGet and versioned Docker images.
- Keep stable package-manager channels on stable releases.
- Make a failed or partially completed publication safe to rerun.

## Creating a release

1. Confirm that CI for the release commit on `main` is green.
2. In GitHub, choose **Draft a new release**.
3. Create a tag containing the complete SemVer version, for example `2.2.0` or `2.2.0-rc.1`, against the release commit.
4. Generate or write the release notes.
5. Mark versions with a prerelease suffix as prereleases.
6. Publish the release.

Publishing the release triggers the release workflow. The workflow validates the tag, checks out that tag, builds the release contract, and publishes the appropriate channels. No separate workflow dispatch should be needed for a normal release.

## Release contract

The build stage should always produce Actions artifacts before any external publication:

- self-contained archives for every supported runtime identifier;
- Windows MSI installers;
- Debian packages;
- the `grate` .NET tool package;
- the six database/library NuGet packages;
- SHA-256 checksums and a machine-readable release manifest;
- the multi-architecture Docker image, built without pushing during CI.

Pull requests build and validate this contract without publishing it. A release run downloads the already-built artifacts into final publication jobs. This keeps packaging logic shared between CI and releases, and prevents a half-complete GitHub release from being assembled by independent jobs racing to upload assets.

## Publication policy

| Destination | Stable release | Prerelease | Notes |
| --- | --- | --- | --- |
| GitHub release assets | Publish | Publish | Upload all archives, MSI files, Debian packages, checksums, and the release manifest. |
| NuGet (`grate` tool and libraries) | Publish | Publish | Use the complete tag as `PackageVersion`, including a prerelease suffix. |
| Docker Hub (`erikbra/grate`) | Version tag and `latest` | Version tag only | Never move `latest` to a prerelease. |
| WinGet (`erikbra.grate`) | Submit update | Skip | Run only after the GitHub assets are available. |
| Homebrew (`erikbra/cask/grate`) | Update cask | Skip | Update both architecture checksums and use `grate-devs/grate` release URLs. |

GitHub automatically supplies source archives for each release tag.

## Distribution ownership boundaries

The source repository moved from `erikbra/grate` to `grate-devs/grate`, but the existing package identities did not move with it. Redirects keep many old download links working; they do not grant a workflow permission to publish to a package registry or another repository.

Each external destination therefore has its own publication job and credential boundary:

- GitHub releases and assets belong to `grate-devs/grate` and use the repository `GITHUB_TOKEN`.
- NuGet package IDs retain their existing ownership and use NuGet trusted publishing with `NUGET_USER`.
- Docker images remain in `erikbra/grate` and use `DOCKER_HUB_USER` plus `DOCKER_HUB_TOKEN`.
- the WinGet package identifier remains `erikbra.grate` and uses `WINGET_GH_PAT` to submit a manifest pull request to `microsoft/winget-pkgs`;
- the Homebrew cask remains in `erikbra/homebrew-cask` and requires a new `HOMEBREW_TAP_TOKEN`, or equivalent GitHub App credentials, with contents write access to that repository.

Canonical download URLs generated by new releases should use `github.com/grate-devs/grate`, even when the registry/package identifier still contains `erikbra`.

## Workflow layout

The workflow split is:

- `ci.yml`: fast build, tests, and analysis for branches and pull requests;
- `build.yml`: the release-artifact build, triggered without publishing for relevant pull requests and pushes to `main`, and with publishing by `release: types: [published]`.

The release event is suitable for stable and prerelease publication. It provides the tagged commit as the event SHA and the release tag as the event ref. A manual dispatch accepting an existing release tag is available only for validation and recovery.

## External publication and credentials

Publishing jobs that use long-lived credentials should use protected GitHub environments so those credentials are unavailable to pull-request builds.

- NuGet: the existing OIDC trusted-publishing policy and `NUGET_USER` repository secret. Do not add an environment to this job without updating the NuGet.org trusted-publisher policy at the same time, because an environment changes the GitHub OIDC subject.
- Docker Hub: `docker-hub` environment with `DOCKER_HUB_USER` and `DOCKER_HUB_TOKEN` repository secrets.
- WinGet: `winget` environment with the `WINGET_GH_PAT` repository secret, used by `wingetcreate update ... --submit` to open the manifest PR.
- Homebrew: `homebrew-cask` environment with a new `HOMEBREW_TAP_TOKEN` secret. Preferably replace this initial fine-grained token with a GitHub App installation token later.

The repository-scoped `GITHUB_TOKEN` cannot update the separate Homebrew tap repository.

## Legacy documentation URL

`https://erikbra.github.io/grate/` currently returns 404. Do not recreate an `erikbra/grate` repository just to host a redirect: reusing the old repository name would remove GitHub's repository redirect to `grate-devs/grate`.

Instead, publish the redirect from the existing `erikbra/erikbra.github.io` user-site repository:

- add `grate/index.html` to redirect the old documentation root;
- add a conditional root `404.html` that redirects requests beginning with `/grate/` to the same path under `https://grate-devs.github.io/grate/`;
- preserve the query string and fragment in the JavaScript redirect;
- provide a canonical link and a visible fallback link for browsers with JavaScript disabled.

GitHub Pages cannot return a true server-side 301 or 302 for these static files. The root page can use an immediate HTML redirect, while legacy deep links necessarily pass through the user site's static 404 page before redirecting in the browser.

## Validation and recovery

Before external publication, the workflow should reject:

- tags that are not valid SemVer;
- a prerelease tag on a release not marked as a prerelease, or the reverse;
- a release tag that does not point to the intended commit;
- missing or duplicate release artifacts;
- an artifact whose embedded/package version differs from the release tag.

Publication steps should be idempotent where the destination permits it. GitHub asset uploads use replacement semantics, NuGet uses `--skip-duplicate`, and recovery runs use the existing release tag rather than creating another release.
