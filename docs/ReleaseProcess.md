# Release process

This document describes the release process introduced for
[issue #796](https://github.com/grate-devs/grate/issues/796).

## Goals

- Use a published GitHub release and its tag as the source of truth for the version.
- Build the same packages and platform artifacts in pull requests and releases.
- Publish all supported distribution formats from one release workflow.
- Support SemVer prereleases, including NuGet and versioned Docker images.
- Keep stable package-manager channels on stable releases.
- Make a failed or partially completed publication safe to rerun.

## Creating a release

1. Confirm that CI for the release commit on `main` is green.
2. In GitHub, choose **Draft a new release**.
3. Create a tag containing the complete SemVer version, for example `2.2.0` or `2.2.0-rc.1`, against the release commit.
4. Generate or write the release notes.
5. Mark versions with a prerelease suffix as prereleases.
6. Publish the release.

Publishing the release triggers the release workflow. The workflow validates that the tag identifies the event commit, checks out that immutable commit, builds the release contract, and publishes the appropriate channels. No separate workflow dispatch should be needed for a normal release.

## Release contract

The build stage should always produce Actions artifacts before any external publication:

- self-contained archives for every supported runtime identifier;
- Windows MSI installers;
- Debian packages;
- the `grate` .NET tool package;
- the six database/library NuGet packages;
- SHA-256 checksums and a machine-readable release manifest;
- the multi-architecture Docker OCI archive, built and digest-verified without pushing during CI.

Pull requests build and validate this contract without publishing it. A release run downloads the already-built artifacts into final publication jobs. This keeps packaging logic shared between CI and releases, and prevents a half-complete GitHub release from being assembled by independent jobs racing to upload assets.

## Publication policy

| Destination | Stable release | Prerelease | Notes |
| --- | --- | --- | --- |
| GitHub release assets | Publish | Publish | Upload all archives, MSI files, Debian packages, checksums, and the release manifest. |
| NuGet (`grate` tool and libraries) | Publish | Publish | Use the complete tag as `PackageVersion`, including a prerelease suffix. |
| Docker Hub (`gratedevs/grate` and compatibility `erikbra/grate`) | Version tag and `latest` | Version tag only | Promote the verified OCI archive with OIDC, then copy its immutable digest with the retained legacy token. |
| WinGet (candidate `grate-devs.grate`) | Prepare candidate; no submission | Skip | Inspect the final GitHub assets and retain new-ID manifests for review. Historical `erikbra.grate` versions stay unchanged. |
| Homebrew (`erikbra/cask/grate`) | Update cask | Skip | Update both architecture checksums and use `grate-devs/grate` release URLs. |

GitHub automatically supplies source archives for each release tag.

## Distribution ownership boundaries

The source repository moved from `erikbra/grate` to `grate-devs/grate`, but the existing package identities did not move with it. Redirects keep many old download links working; they do not grant a workflow permission to publish to a package registry or another repository.

Each external destination therefore has its own publication job and credential boundary:

- GitHub releases and assets belong to `grate-devs/grate` and use the repository `GITHUB_TOKEN`.
- NuGet package IDs retain their existing ownership and use NuGet trusted publishing with `NUGET_USER`.
- Canonical Docker images use `gratedevs/grate` and the organization OIDC connection in `docker-hub`. The `erikbra/grate` compatibility copy uses the retained `DOCKER_HUB_USER` and `DOCKER_HUB_TOKEN` secrets.
- WinGet preparation emits only the proposed `grate-devs.grate` identity. The accepted public package remains `erikbra.grate` until migration acceptance; corrected MSIs must never be submitted as an old-ID update. See [WinGet migration and Windows test evidence](../installers/winget/MIGRATION.md);
- the Homebrew cask remains in `erikbra/homebrew-cask` and requires a new `HOMEBREW_TAP_TOKEN`, or equivalent GitHub App credentials, with contents write access to that repository.

Canonical download URLs generated by new releases should use `github.com/grate-devs/grate`, even when the registry/package identifier still contains `erikbra`.

## Workflow layout

The workflow split is:

- `ci.yml`: fast build, tests, and analysis for branches and pull requests;
- `build.yml`: the release-artifact build, triggered without publishing for relevant pull requests and pushes to `main`, and with publishing by `release: types: [published]`.

The release event is suitable for stable and prerelease publication. It provides the tagged commit as the event SHA and the release tag as the event ref. A manual dispatch accepting an existing release tag is available for validation and guarded recovery. Select that same tag as the workflow ref: the event ref must be `refs/tags/TAG`, and the tag must resolve to the event SHA. Every source checkout uses the event SHA, so a dispatch on `main` cannot select and execute another tag in the default branch cache context. Publishing is disabled by default. Draft releases cannot enable publishing. For a partially published Docker version, rerun the failed publishing jobs in the original tagged release run so they reuse its verified archive; a fresh publishing run rejects a conflicting existing version before any GitHub asset replacement.

For validation only, dispatch on a release tag that contains this workflow:

```sh
gh workflow run build.yml --repo grate-devs/grate --ref 2.3.4 -f release_tag=2.3.4 -f publish=false
```

For guarded recovery against an existing published release, use the same command
with `-f publish=true`. A dispatch without `release_tag` and with `publish=false`
builds its selected workflow commit using GitVersion. Old tags use the workflow
stored at those tags; they cannot borrow current `main` tooling under this policy.
Do not move a historical tag to introduce newer tooling. Rerunning a historical
manual run on `main` also retains its old workflow and source context; it does
not apply this source-isolation fix.

## External publication and credentials

Only publishing jobs reference external publishing credentials. Environment association does not change the scope of existing repository secrets; ordinary build/test jobs have no credential references, and publishing eligibility is enforced by the release resolver and job conditions. Docker environment ref policies additionally limit which refs can use its OIDC identity.

- NuGet: the existing OIDC trusted-publishing policy and `NUGET_USER` repository secret. Do not add an environment to this job without updating the NuGet.org trusted-publisher policy at the same time, because an environment changes the GitHub OIDC subject.
- Docker Hub: `docker-hub` environment with `DOCKERHUB_OIDC_CONNECTIONID` for canonical publication and the retained `DOCKER_HUB_USER`/`DOCKER_HUB_TOKEN` repository secrets for compatibility. No manual environment approval is configured; ordinary builds cannot use the OIDC identity. See [Docker release details](../installers/docker/RELEASE.md).
- WinGet: preparation uses only the read-only repository `GITHUB_TOKEN` to inspect public release metadata and upstream templates. It has no publishing environment, PAT reference or submission command. Retained `WINGET_GH_PAT` credentials are not used by this workflow; activating upstream submission is a separate change after the #800 acceptance steps.
- Homebrew: `homebrew-cask` environment with a new `HOMEBREW_TAP_TOKEN` secret. Preferably replace this initial fine-grained token with a GitHub App installation token later.

The repository-scoped `GITHUB_TOKEN` cannot update the separate Homebrew tap repository.

## Legacy documentation URL

`https://erikbra.github.io/grate/` currently returns 404. Do not recreate an `erikbra/grate` repository just to host a redirect: reusing the old repository name would remove GitHub's repository redirect to `grate-devs/grate`.

Instead, publish the redirect from the existing `erikbra/erikbra.github.io` user-site repository:

- add `grate/index.html` to redirect the old documentation root;
- add a conditional root `404.html` that redirects requests beginning with `/grate/` to the same path under `https://grate-devs.github.io/grate/`;
- preserve the query string and fragment in the JavaScript redirect;
- provide a canonical link and a visible fallback link for browsers with JavaScript disabled.

GitHub Pages cannot return a true server-side 301 or 302 for these static files. The root page can use an immediate HTML redirect, while legacy deep links necessarily pass through the user site's static 404 page before redirecting in the browser.

## Validation and recovery

Before external publication, the workflow should reject:

- tags that are not valid SemVer;
- a prerelease tag on a release not marked as a prerelease, or the reverse;
- a release tag that does not point to the intended commit;
- missing or duplicate release artifacts;
- an artifact whose embedded/package version differs from the release tag.

All artifact jobs use the immutable workflow event SHA, after verifying any release tag resolves to that commit. Docker publication downloads the already verified OCI archive, without rebuilding; existing version tags with a conflicting digest are rejected in the build preflight before the release gate can permit GitHub uploads. The release-ready gate certifies packaging and policy checks; the separate test job and required CI checks provide application-test evidence. Do not rebuild or blindly retry a partially published Docker version; retain and reuse its original verified artifact/digest.

Publication steps should be idempotent where the destination permits it. GitHub asset uploads use replacement semantics, NuGet uses `--skip-duplicate`, and recovery runs use the existing release tag rather than creating another release.

## WinGet migration handoff

The MSI/WinGet preparation code and disposable Windows tests for #800 are
integrated in this release workflow. Before the release-ready gate can pass, both
MSI build jobs run the manifest/identity contract tests and inspect the actual
MSI ProductCode, stable architecture UpgradeCode, publisher, version, platform
and per-user context. The existing 13-file release contract is retained.

After stable GitHub assets have been uploaded, `prepare-winget` uses the pinned,
checksum-verified wingetcreate tool and `Create-Installer.ps1 -PrepareMigration`.
The helper verifies the uploaded asset inventory and MSI digests/metadata before
schema-validating the complete manifest set with pinned WinGet 1.29.380 and
retaining a `winget-migration-candidate-VERSION` Actions artifact with tool/source
provenance and the schema log. It does not
submit to `microsoft/winget-pkgs`, update the old ID or enable the new public ID.
PRs, ordinary builds, validation-only dispatches and prereleases skip this step.

For #800, review and install-test the final candidate, submit the new
package separately, and verify it after acceptance through `--source winget`.
MSI users transition by installing the new ID, which performs the transactional
legacy upgrade. Portable ZIP users explicitly uninstall the old ID and install
the new one. Keep public installation instructions on the accepted identity
until that handoff is complete. Full commands and evidence limits are in the
[WinGet migration guide](../installers/winget/MIGRATION.md).

### Prerelease MSI identity

Windows Installer stores a numeric three-part ProductVersion. The full SemVer
release version is also passed to the MSI builder so prereleases receive distinct
ProductCodes; stable ProductCodes and architecture UpgradeCodes stay unchanged.
Different releases with the same numeric core (for example `2.2.0-rc.1`,
`2.2.0-rc.2` and `2.2.0`) require explicit uninstall/reinstall. The installer
refuses that switch before changing an existing installation. Normal upgrades
to a higher numeric version retain the tested stable major-upgrade path.
WinGet preparation remains stable-only.

For local workflow-policy checks, install the pinned YAML parser in a temporary
virtual environment with `python -m pip install -r eng/requirements-workflow-tests.txt`,
then run `python -m unittest discover -s eng -p 'test_*.py'`. The MSI build jobs
run the PowerShell contract tests on Windows and verify the actual built files;
local checks on another OS do not establish native installer behavior.
